# Beginner's Guide to the RazorPay Transaction Fraud Detection Project

Welcome to the project! This document explains the core concepts, the project structure, the role of each file, and the architectural decisions we made along the way.

## What is this project?
This project aims to detect **fraudulent transaction spikes** in a financial stream. In real-world scenarios (like those handled by RazorPay), attackers might use compromised accounts to rapidly cash out funds or automate high-frequency transactions. This project builds a machine learning pipeline to spot these rapid anomalous "bursts" of activity without introducing data leakage.

## Core Concepts & Key Decisions

1. **The Dataset (PaySim)**
   * **Decision:** We used the publicly available PaySim dataset.
   * **Reasoning:** Since real-world transaction datasets are kept strictly private due to PII and security concerns, PaySim provides a solid structural foundation of mobile money transactions. 

2. **Synthetic Spike Injection**
   * **Decision:** We built our own module to inject synthetic spikes.
   * **Reasoning:** Typical datasets lack explicit labels for rapid, automated "spike" attacks. We layered controlled fraudulent bursts over the normal PaySim traffic across different "difficulty tiers" to train and test our models effectively.

3. **Strict Temporal Evaluation (No Leakage)**
   * **Decision:** Time-based splitting (Train < Step 500, Val: 500-600, Test > 600) and strict rolling windows.
   * **Reasoning:** If you use future data to predict the present, the model looks great in testing but fails in production. Our feature engineering computes metrics up to the *exact moment* before a transaction happens.

4. **Business-Cost Optimization over F1 Score**
   * **Decision:** We tuned our models using a custom Cost Engine (False Positives = ₹500, False Negatives = ₹10,000).
   * **Reasoning:** In fintech, missing a fraud case (FN) costs a lot of money (chargebacks, lost funds), whereas mistakenly blocking a real user (FP) costs friction and manual review time. Optimizing purely for accuracy or F1 score ignores this asymmetry. LightGBM was ultimately chosen because it minimized this total expected cost.

## Project Structure & Important Files

Here is a breakdown of what each file and directory does:

### `src/` (Source Code)
The brain of the project.
* **`src/features.py`**: The Feature Engineering engine. It calculates rolling window statistics (velocity, volume, destination entropy) across time. Crucial for ensuring zero data leakage.
* **`src/spike_injection.py`**: The module that artificially inserts rapid bursts of transactions (spikes) into the base dataset to simulate an attack.
* **`src/evaluate.py`**: Contains the Cost Engine and evaluation metrics. It figures out the best threshold for our models based on real-world financial costs rather than just accuracy.
* **`src/explainability_extraction.py` / `src/explain.py`**: Used to generate explanations (like SHAP values) to understand *why* the model flagged a transaction as a spike.
* **`src/model_comparison_final.py`**: A utility used to run the final showdown between our different models.
* **`src/models/` (Directory)**: Contains the actual model logic.
  * `lightgbm_detector.py`: Our final supervised model that won the evaluation.
  * Isolation forest and baseline z-score implementations for our baselines.

### `scripts/` (Executable Pipelines)
These are the files you actually run to execute the pipeline.
* **`scripts/build_features.py`**: Reads the raw data, runs it through `features.py`, and saves the engineered dataset.
* **`scripts/generate_synthetic_spikes.py`**: Executes the spike injection.
* **`scripts/run_models.py` / `scripts/run_all_evaluations.py`**: Scripts to train the models and run them against the validation/test sets.

### `reports/` (Outputs)
* **`reports/final_model_comparison.md`**: The final markdown report comparing the Z-Score, Isolation Forest, and LightGBM models.
* **`reports/explainability_report.md`**: Shows which features (e.g., rapid velocity) the model relied on most heavily.
* **`*.json` / `*.png`**: Metric outputs and graphs (like Precision-Recall curves) generated by the evaluation scripts.

### Root Files
* **`README.md`**: The high-level executive summary of the architecture and results.
* **`pyproject.toml` / `uv.lock`**: Dependency management files. They list all the Python libraries (like pandas, scikit-learn, lightgbm) required to run the project.

## Summary of the Final Outcome
After engineering the features and tuning the thresholds based on the cost function, **LightGBM** was selected as the final model. It achieved near-perfect recall on our synthetic test set while drastically minimizing false positives, dropping the estimated operational cost to ₹2,100 (compared to ₹54,000 for the baseline). We also conducted degradation testing to find exactly how "slow" an attack needs to be before our model fails to catch it.
